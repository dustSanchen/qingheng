## 第一档 · 零成本，本周可做

- [ ] **A5 · 推送到达真机验收**（唯一只能靠时间的项）
  连续观察 3 天：07:00 / 20:30 是否准时送达、正文是否正常；三天后核对
  `adviceHistory` 里 api / fallback 的比例与实际到达时间。这是前台服务改造（P1-5）的最终验收。
- [ ] **C3 · 第三家模型服务商**
  加一个 OpenAI 兼容服务商（如硅基流动），纯配置层改动（服务商注册表 + 默认地址/模型）。
  动机：B.AI 余额耗尽曾中断迭代，服务商单点是当前最现实的日常风险。约半天。
- [ ] **真机完整回归**
  覆盖安装最新版后过一遍核心旅程：记餐（拍照/语音/文字）→ 确认 → 趋势 → 问答 → 导出。
  最近十轮改动集中在 UI 与存储，值得一次人工回归确认无交互回归。

## 第二档 · 中型迭代（每轮半天～一天）

- [ ] **B8 · 渲染性能第二阶段**
  1. 问答记录分页渲染：`renderChat` 目前一次性渲染全部匹配记录；改为默认渲染最新 30 条 +
     「更早的记录（还有 N 条）」按钮，搜索过滤后同样套用上限。存储上限 200 条，历史增长后这是最先卡的地方。
  2. 脏标记重渲染：`renderBody` 每次触发 15 个渲染器全量跑；保存餐食后只重渲餐食相关区块。
     分页先行，脏标记视实测卡顿再决定深度。
- [ ] **B9 · 剩余 localStorage 收编**（目标：换手机零丢失）
  - `qingheng.chat.unhelpful`（"这条没用"标记）→ `/api/prefs`，随备份与迁移走
  - `qingheng.chat.web`（联网检索开关）→ `/api/prefs`
  - `qingheng.training.consent`（训练建议同意记忆）→ `/api/prefs`
  - `qingheng.tab`（纯视图状态）明确可弃
  注意：`unhelpfulChats` 是启动时读入内存的 Set，水合时需同步刷新内存；
  `#chat-web` 复选框的勾选态也要在水合后回写。
- [ ] **B10 · 样式令牌收尾**
  1. 棘轮断言：`styles.css` 硬编码 hex 总量只减不增（先锁定当时基线）。
  2. 分批收敛：优先替换与既有令牌**同值**的字面量（零视觉变化），再逐批处理 02-color-groups.csv 列出的语义组。
  3. 测试断言抗重构：把源码逐字断言逐步改成行为/结构断言（本轮多次被逐字断言绊住，教训已记录）。

## 第三档 · 战略决策（需要产品负责人拍板）

1. **Health Connect 根因**（2026-10-17 遗留）
   侧载包不被 HC 登记为健康数据应用，五项读权限无从授予，手表数据靠手记。
   选项：**Play 内测轨道**（最可能根治，顺带消掉 `USE_EXACT_ALARM` 的上架政策风险）／
   继续手记 ／ 小米运动健康导出文件导入（需确认导出格式）。
2. **发布形态**
   继续侧载 or Play or 国内市场。决定签名策略、隐私声明、更新机制的走向。
   若坚持侧载：写一页「换新手机迁移指引」给朋友群（迁移包校验已支持，只差文档）。
3. **纸感暗色变体**
   「自动 + 系统深色」目前全程账本暗色；喜欢纸感排版的用户夜间没有选择。
   产品口味问题，成本约一轮（账本暗色的令牌骨架可直接复制）。

## 建议执行顺序

```
本周：A5 观察为主 + C3 顺手做掉 + 真机回归
之后：按真实使用反馈定优先级——
  记录流畅           → B9（换机零丢失）→ B8 → B10
  朋友群开始有人用   → C1/C2 渠道决策优先
  数据量明显增长     → SQLite 读路径聚合提上日程
```

## 工程纪律（每轮不变）

1. 改 fragments / Java 源，跑 `tools\assemble-app.ps1`，`node tools/test-all.mjs` 全绿。
2. `tools\dev-loop.ps1 -Version <新版本> -VersionCode <+1>` 构建装机冒烟。
3. 提交（中文消息，`git commit -F <文件>`）后双推送：`git push origin master` + `git push localmirror master`。
4. RUNLOG-codex.md 追记一行；本文档勾掉对应条目。
