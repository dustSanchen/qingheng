## 一、「用 AI 排今天」的结果呈现

现状证据：`docs/shots/after2/record-training-2.png`

**问题**
- 每个动作竖排三行（勾选框 / 名称 / 组次重量），一个动作占约 200px，6 个动作要滚两屏
- 勾选框居中悬在动作名上方，不在行首，读起来像装饰
- 标题写「今日顺序」，但列表里没有任何序号
- 「用 AI 排今天 / 修改 / 清除」夹在同意勾选与列表之间，主行动被埋在中段
- 「6 个动作」在标题右侧，但它想表达的总量（组数、预计时长）没有

**必须做到**
1. 单动作收敛成**一行**，高度 ≤72px，结构包含：勾选、序号、动作名、组×次×重量
2. 序号必须可见（这是"顺序"的意义所在）
3. 6 个动作在 360×800 的屏里至少看到 4 个
4. 主行动按钮 ≤2 个，且在列表上方一次性给全；「修改/清除」降为次按钮或行内操作
5. 给出今日汇总：总组数、预计时长（用已有数据推算，不要编）
6. 「45 kg」「8 次」这类数字与单位不得跨行拆分

**保留**：同意勾选（合规必需），但必须完整可见、不被底部导航遮挡（审计 #1）。

## 二、训练计划的文字排布

现状证据：`docs/shots/after2/record-training.png`（顶部卡片）与 `-2.png`（长段落）

**问题**
- 「侧平举下放只到全程的 2/3…计划里的 12/10/8 次不是 RM（力竭次数），而是每组留约 2 次余量（RPE 8）」是一整块无结构散文，行宽过长、`RM`/`RPE` 夹在句中
- 「今天休息；下一个训练日 11-02 · 推 · 卧推」三件事挤在一行 chip 里
- 「本周负荷偏高（ACWR > 1.5），按减载周安排：负重 ×0.9、组数 -1」是段落，不是数据

**必须做到**
1. 状态信息拆开：今天（休息 / 训练日）→ 下一个训练日 → 具体分化，各占一行或一栏
2. 依据类内容（ACWR、减载幅度）做成**数据条**而不是句子：标签 + 数值 + 判定
3. 解释性文字下沉到可折叠块，默认收起；首次出现的术语（RM / RPE / ACWR）就地给 4–8 字解释
4. 中文行宽控制在 18–24 字/行，不得出现单字成行

## 三、拍照 / 从相册选的一致性

现状证据：`docs/shots/after2/record.png` 底部两张上传卡

**问题**
- 两个入口视觉权重相同，但行为完全不同（一个唤起相机、一个打开相册）
- 图标风格与尺寸不统一（相机 vs 图片），文字长度也不等（2 字 vs 4 字）
- 旁边的「语音」是第三种输入方式，形状却是竖长条，与这两张卡不在一个体系里

**必须做到**
1. 三种输入（拍照 / 相册 / 语音）用同一套尺寸与圆角规则；要么三卡并列等宽，要么收进一个「添加」底部弹层
2. 主次明确：拍照是主路径（多数人先拍），相册为次
3. 覆盖三种异常态：无相机权限、相册取消、图片过大 —— 各给文案与样式
4. 与 B 组已定的按钮 / 底部弹层规范保持一致，不要另造一套

## 验收

| 项 | 标准 |
|---|---|
| 单动作行高 | ≤72px |
| 360 宽首屏动作可见数 | ≥4 |
| 数字与单位 | 无跨行拆分 |
| 术语 | RM/RPE/ACWR 首次出现有解释 |
| 中文行宽 | 18–24 字/行，无单字成行 |
| 输入入口 | 三者同一尺寸体系，主次分明 |
| 对比度 | 正文 ≥4.5:1，控件边界 ≥3:1 |
