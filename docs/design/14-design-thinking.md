# 14 · 设计思考的表达：学 Claude 的「怎么想」，不是「用什么字体」

> 13 号文档解决「看起来对」，本文解决「说得清为什么对」。
> Claude 系真正稀缺的不是奶油底色，而是**把设计决策写成可复现的推理**。
> 本仓库的交付格式（三行：改了哪些文件 / 诊断结论 / 设计理由）就是这条线的入口。

## 1. 八条思考习惯

| # | 习惯 | 反例（常见写法） | 正例 |
|---|---|---|---|
| 1 | **先定不可协商项** | 「我建议用圆角 12px」 | 「触控目标 ≥44px 是硬约束，所以圆角只能 12 起」 |
| 2 | **以信息层级为单位决策** | 「这页要更现代」 | 「这页有三个层级：结论 / 依据 / 操作。现在三者同权重」 |
| 3 | **每个选择配一个被放弃项** | 「改成 8px 间距」 | 「8px 而非 4px：这里要分组，4px 会让两组看起来同级」 |
| 4 | **用可验证断言替代形容词** | 「线条太粗」 | 「1px 线 + 2px 内阴影叠加，屏幕上读作 3px」 |
| 5 | **先排状态矩阵再谈样式** | 只做「有数据」态 | 空 / 加载 / 错误 / 超长 / 极端数值 五态各自定义 |
| 6 | **把「不做」写进交付** | 顺手改了无关间距 | 「本轮不动纸感；账本表格线是唯一改动面」 |
| 7 | **结论先行，证据在后** | 先讲十分钟背景 | 第一行结论，后面才是截图与行号 |
| 8 | **让文档能被脚本检验** | 「字号保持四级」 | 「`aesthetic-audit.mjs` 的字号计数不得上涨」 |

## 2. 交付模板（替代「我改了样式」）

```
现状判定：现在发生什么（现象 + 证据：截图路径 / 代码行号 / 审计数字）
归因：为什么这样（宽度 / 颜色 / 叠加？层级？状态缺失？）
结构决策：改哪些层，按什么规则
取舍：选 A 不选 B，因为 …（一条就够，必须具体）
验证：命令 + 结果（assemble / test-all / 装机截图 / audit 计数）
```

判据很简单：**别人不看界面、只读这段说明，能不能复现你的判断**。不能，就还是形容词堆砌。

## 3. 应用到本仓库的账本线条任务

一个合格的「诊断结论」长这样：

> 现状判定：账本皮肤记录页的分段容器与卡片各有一道 1px 边框，卡片内层再叠 1px 内阴影，
> 在 3x 屏上渲染为 2.33px 实线观感（截图 build/records-ledger-*.png，样式 L600/L358）。
> 归因：不是宽度问题，是**两层线叠加 + 线条色接近正文墨色**。
> 结构决策：容器保留 1px 墨色 10% 发丝线，卡片去掉内阴影，只留分组间距。
> 取舍：不加宽、不删除分组线——删了分组会塌，加宽会更粗。
> 验证：assemble → test-all 55/55 → 装机截图三态对比 → audit 灰线计数 3→0。

这段里没有一句「更精致」「更现代」，但任何人都能照着复现。

## 4. 评审一份设计说明的四问

1. **有没有现状判定**？只讲目标不讲现在的，通常是没看过现状。
2. **归因是否落到机制**（宽度/颜色/叠加/层级/状态），还是停在感受？
3. **有没有被放弃的选项**？没有取舍的说明，等于没做决策。
4. **验证是否可复跑**？给不出命令与结果的，视为未完成。

## 6. 一句话

> **设计说明不是汇报，是让别人能复现你判断的推理链；写不出取舍，就等于没做设计。**
